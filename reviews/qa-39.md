## Findings (round 5)

### F4 — `references/hansei.md` §5 step 6 and `skills/run/SKILL.md` step 8.6 (contract 39-standard-changes, L8/L9) — minor, does not block — `$w` from the guard does not survive into a separate shell call

- **Reproduction.** In a scratch repo, with the item in `../wt/12` and the shell in the main checkout, run the guard in one shell. Then run step 6.1's and 6.2's commands in a new shell, with `rm` replaced by `echo`. The Lead's Bash tool starts each call in a fresh shell, so `$w` is unset there:
  - `git -C "" add -- "work/12/[0-9][0-9]-*.md"` acts on the shell's working directory, here the main checkout. The result is `fatal: pathspec … did not match any files`, rc 128, and `add -u` gives the same.
  - `git rm` fails, so the `&&` chain stops.
  - The `rm -rf` target would have been `/work/12`.
- **Expected.** The text says every command "names the worktree by its absolute path, so the shell's working directory does not matter". Nothing outside the worktree is ever addressed.
- **Actual.** Correctness depends on running guard, 6.1 and 6.2 in **one** shell call. The text never says so, though it does say a `cd` does not persist. Split across calls, the close fails loudly in the main checkout (safe, thanks to `&&` and the main checkout having no `work/<id>`). But it names a path outside the worktree, and the Lead is left to improvise.
- **Required fix** (developer; one sentence and two characters):
  - say "run steps 0–2 as one shell call";
  - write `"${w:?}/work/<id>"` (or add `[ -n "$w" ] ||` to the chain), so an empty `$w` can never reach `rm`.

  Recommended before merge; it does not block the release.

### F5 — `scripts/cut-offs.sh` sleep test (contract 39-plugin-scripts §4, *Sleep*) — low — a `Wake` line alone inside a gap counts as asleep

- **Reproduction.** Use `tests/factory/test_cut_offs.sh`, check `sleep-wake-inside-alone-not-asleep` (a skip). The sleep log holds `Wake 23:00Z` and `Wake 23:55Z`, with no Sleep line. The gap is `23:50:46Z–open` (last marker 00:05:54Z).
- **Expected.** The contract says asleep means "a `Sleep` line inside the gap, or the last `Sleep`/`Wake` line before the start is `Sleep`". So this gap is `stalled`.
- **Actual.** `interrupted`. The script counts any event inside the gap (`select(.t >= $g.start and .t <= $e)` has no `.k == "Sleep"`).
- **Impact.** The kind label only: both kinds are held waits, never agent working. A Wake implies an earlier sleep, so this is arguably the better reading. Either the developer adds the `Sleep` filter, or the architect words the contract to match.

### Observations (no finding)

- **Start when the notice left no marker.** *Taking the start* takes the **last** line's start at a notice. If the stopped agent's transcript shows earlier recovered cut-offs but none for this notice, the last line is an older gap. An example is a limit notice whose transcript holds no `rate_limit` entry. The start is then too early, and agent working is undercounted. This fails towards a wait (the contract's direction), and in the demo every notice had its marker. A tighter rule would be "the last line, if its end is `open` or after the agent's last entry; otherwise the transcript's last non-marker entry".
- **The close's `rm -rf -- "$w/work/<id>"` may trigger Claude Code's built-in removal safety check** in the Lead's session. In this QA session that check stopped two of my scratch commands that ran `rm -rf` on a shell variable. I did not try to work around it, and I did not delete those scratch directories. If it fires at close in an AFK run, the prompt times out and the close stops. That is visible only in a real session: see the AC-18 human-only check.
- The demo's lead state on factory-sandbox `item/2` was last committed at *Open PR* (the v1 close problem fixed in round 4). Rows 5 onward came from git commit times and the transcripts.
