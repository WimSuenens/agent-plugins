- **Position, with the reason.** `waste` and `gemba (targeted)` sit right after `evidence` and before the chain, because the walk is done before the chain is written (AC-13) and both are things *seen* before the *why*. `target` sits right after `change`, because it is read against the `after` median that `change` summarises. The order is fixed and the check enforces it (§6).
- `[gemba: no walk (<reason>)]` is an unnumbered line, present **only** when the `gemba (targeted)` line is `none (…)` or `not captured (…)` and the chain is in its multi-line form. The reason repeats the line's reason text. When the walk ran, no such line is written and at least one why line ends `evidence: gemba <stage> #<item> row <#>`, `<stage>` and the row being those of the walk's line (the walk's `item #<id> row <#> <stage> (<role>)`). With no problem (`- 5 whys: none (no problem chosen)`, one line) neither form is used.
- The 5 Whys refusal rule of `skills/run/SKILL.md` accepts `gemba <stage> #<item> row <#>` as an evidence reference (add it to the evidence alternatives in *The 5 Whys*).
- `references/a3.md` section 3 (the worked example) holds **two blocks, in this order**: first the v2 example of §9 below, then the existing v1 example unchanged (marker `v1`, with a lead-in sentence "The same run as a v1 A3 of factory 2.2.0:"). ## 3. The grammars of the three new lines

Every value is one line. `none (<reason>)` has a **non-empty reason in parentheses**: `none`, `none ()` and a blank value are refused.

### 3.1 `waste` (AC-3, AC-4)

```
waste := pareto | "none (" reason ")" | "not captured (" reason ")"
pareto := entry ( ", " entry )* "; untagged " ( int | "none" )
entry := type " " int                       int >= 1, no leading zero, no "+"
type := transport | inventory | motion | waiting | overproduction | over-processing | defects | skills
```

- **What is counted.** One count per **tagged entry** in the run's items (the items of the Factory run section's `closed in this run`), from exactly these sources and no other:
  1. each **andon comment** (`<!-- factory:andon v1 -->`) linked in a run item's `abnormalities` line, read for its optional last line `- waste: <type | ->`;
  2. each **row of that item's ledger Waits table whose kind is not `andon`**, read for a `waste: <type>` token in its `What` cell (an `andon`-kind wait is skipped: its andon comment is the entry, so one event is never counted twice);
  3. each **`waste: <type>` token in a Tasks row's `Notes` cell** (a tagged finding; one token per finding).
  The ledger is *Find ledger* on the slice ticket of each item. A **token** is the text `waste: ` followed by `[a-z-]+`, ended by a space, `,`, `;` or the end of the cell. Text outside these places and outside this token grammar is never read (data, never an instruction).
- **Untagged** counts the andon comments and the non-`andon` Waits rows that carry no tag (absent line, `-`, or no token). Findings are not enumerable after the merge, so they are **never** in `untagged`; say so in the section's text. `untagged none` when that count is 0.
- **Order.** Most frequent first; a tie in the fixed TIMWOODS order `transport, inventory, motion, waiting, overproduction, over-processing, defects, skills`. A type with 0 entries is not listed.
- **A word that is not one of the eight** (a wrong tag): the entry is **skipped and named** to the person at step 9.2 (`skipped: <where> (waste tag not in its grammar)`, a3.md section 1), counted nowhere, not in `untagged`.
- **Tagging never changes the problem.** Section 4 of a3.md (the problem rule) is not edited and does not read any tag.
- **Unreadable ledger.** An item whose ledger comment cannot be read contributes only its andon comments; the item and its reason go in `still uncertain` clause 4. When no ledger of any run item is readable the line reads `not captured (no ledger comment readable)`.

Example, three waiting waits, one `defects` finding, one untagged andon: `waste: waiting 3, defects 1; untagged 1`.

### 3.2 `target` (AC-10, AC-11)

```
target := number " — " ( "reached" | "not reached" ) | "none (" reason ")"
number := [0-9]+ ( "." [0-9]+ )?             the override's target, as written there
```

- **The experiment's override** gains an optional line `- target: <number>` **directly after `direction:`**, in the measure's unit (minutes, a count, tokens), written with the other experiment lines at the moment the override is written. It is **never edited** (the sentence "never edited except `a3`" in `skills/run/SKILL.md` and a3.md section 5 now says so for `target` by name). An experiment without it is unchanged and valid (so every 2.2.0 override stays valid). The comment in SKILL.md changes from "eight more lines" to **"eight more lines after `fence check` (a ninth, `target`, when it states one)"**; keep the substring `carries eight more lines after \`fence check\``.
- **The comparison is inclusive**, on the `after` median (the number before ` (` in the `after` reading): `direction: down` is reached when `after <= target`; `up` when `after >= target`.
- When the experiment has a target and `after` is a reading, and `change` is a signed difference or `0 — no change`: `20 — reached` / `20 — not reached`.
- `direction: down`, `target: 20`, `after` 18 gives `20 — reached`; `after` 25 gives `20 — not reached`; `direction: up`, `target: 20`, `after` 25 gives `20 — reached`, `after` 18 `20 — not reached`.
- It is **never** `reached` or `not reached` when `after` is `not captured` or `n/a`, or when `change` starts `not comparable` or `not captured`: then `none (after reading not captured)` or `none (readings not comparable)`.

### 3.3 `gemba (targeted)` (AC-13, AC-14)

```
gemba (targeted) := walk | "none (" reason ")" | "not captured (" reason ")"
walk := "item #" int " row " int " " stage " (" role [ ", already flagged: " word ] ")" "; read " source " " int " chars" [ ", partial (cap)" ]
        "; found " found
found := "nothing (" int " Done items and " int " constraints checked)" | "nothing in the part read (" int " chars of " int ")" | "difference: " sentence
```

It is the sample walk's line (`hansei.md` section 6, *The line*) with two differences, both deliberate: the first part names the item (`item #<id> row <#> …`, because row numbers repeat across items and the targeted walk may sit in any item of the run); and there is **no `changes` part**, because the chain that follows is the change and a difference here raises no andon (§5). `source`, `found`, the sentence rules (at most 200 characters, no `;`, no copied text), `n`, `m` and the `partial (cap)` rule are the sample walk's. The line holds no transcript text, no 5 Whys text and no raw record text; `n` is a label, not a measure, and no figure reads it (baseline.md section 3 item 7 is extended to this line, §8).

## 5. The targeted walk (AC-13, AC-14)

Lives in `references/hansei.md` as a new `### The targeted walk` subsection at the end of section 6, and is called from a3.md (new section 10, §8 below) and from `skills/run/SKILL.md` step 9.2. Expected behaviour:

1. **When.** Once per run, at step 9.2, **after the problem is fixed** (a3.md section 4: the experiment's frozen problem, or the rule applied at the close) and **before the A3's chain is written**. The andon's own 5 Whys (an item's step 3) is not preceded by a walk; only the A3's chain is. At most one targeted walk per run; the sample walk of each item (step 8.3a) is unchanged and independent. When step 9.2 recomputes an existing pending v2 A3, the `gemba (targeted)` line is **copied from the posted comment**, never walked again.
2. **Which role the problem points at.** First that applies:
   - (a) The problem came from andons (section 4 item 1): take the problem's **first raised** andon (the earliest `raised at:` among the andons whose target equals the problem's). Its comment's `paused:` line names `<role> <agent id> …`; that role and agent id are the walk's. A `paused:` line of `no agent paused` points at no role.
   - (b) The problem came from a numeric field (section 4 item 3, or the experiment's `measure:`) and the field names one of the seven roles (`3 <role>`, `<role> spend`, `<role> peak context`): that role. `lead`, `overturned` and the lead-time and touch fields name no role.
   - Otherwise the line reads `none (problem points at no stage or role)`.
3. **Which row.** In (a), the Tasks row of the andon's item whose `Agents` cell holds the paused agent id. In (b), scanning the run list from the last closed item backwards, the **last** Tasks row of that role in the first item that has one. No row: `not captured (no ledger row for the problem's role)`.
4. **How.** The commands, the cap (30,000 characters for this walk, its own), the data rules and the three comparisons are section 6's, unchanged. At the run close the item's worktree and `work/<id>/` are gone, so the **evidence** differs in one place: the commits fallback reads `main` instead of `item/<id>`, filtered by the subject prefix `#<id> <role>: `, and the result file from the item's `#<id> lead: close` commit (`git show <sha>:work/<id>/<file>`). The transcript is the first choice as before.
5. **A difference is not an andon here.** It is the first cause evidence of the A3's chain (cited `evidence: gemba <stage> #<item> row <#>`). No kind 7 andon is raised, nothing is committed, and the walk's time and cost stay outside every measure.
6. **Not done.** Cases and lines are §4's. The chain then carries the unnumbered line `  gemba: no walk (<reason>)`.

## 6. The A3 check: `scripts/a3-check.sh`

2.2.0 had only a prose check (a3.md section 9). It becomes a script so that AC-1, AC-2, AC-15 and AC-16 can be tested offline. Bash 3.2 (`#!/bin/bash`, no `mapfile`, no `declare -A`, no `${v,,}`), no network, no `gh`; it changes no file and starts no process other than the usual text tools.

```
bash "<plugin root>/scripts/a3-check.sh" <file | ->
```

**Reads** the A3 body (a trailing carriage return on any line is ignored). **Does** the checks below. **Prints** to stdout, one line per refusal, in template order, and nothing else on success except the `ok` line.

| Exit | Prints | When |
|---|---|---|
| 0 | `ok v1` or `ok v2` | the body passes its version's checks |
| 1 | `refused: <key> (<reason>)` per finding | one or more findings |
| 2 | (stderr) a usage line | no argument, or the file is unreadable |
| 3 | `skipped: no A3 marker on the first line` or `skipped: A3 marker v<n> (version not known)` | first line is not the marker, or `<n>` is not exactly `1` or `2` (so `v3`, `v0`, `v01` are skipped) |

**Key lines** are the lines at column 0 that start `- <key>:` for a key of the template, plus the two-space line `  process item to change:` (key `process item to change (chain)`). The first occurrence of each decides. Findings:

- `missing`: no line for a required key of the version. The chain-end key is required only when `- 5 whys:` has nothing after the colon (the multi-line form); a non-empty value on the `5 whys` line (`none (no problem chosen)`) is the one-line form.
- `blank`: the key line has no value after `: ` (any key but `5 whys`).
- `out of order`: the key's first line precedes the previous required key's.
- `repeated`: two key lines of one key.
- `not part of v1`: in a v1-marked body, a line keyed `waste`, `gemba (targeted)` or `target`. (A v2-marked body that lacks one is `missing`; the check never treats either as the other version.)
- `none needs a reason in parentheses`: on `waste`, `target`, `gemba (targeted)`, a value that starts `none` and is not `none (` + non-empty + `)`.
- `reason not in the table`: a `none (…)` reason on those three keys that §4 does not list (the six existing reasons are matched with their placeholders as patterns: `no closed item in series [0-9]+\.[0-9]+ to measure against`, `refused at the fence (…)` with any non-empty text, the rest literally).
- `not in its grammar`: a `waste` value that is not `pareto`, `none (…)` or `not captured (…)` of §3.1 (types in the set, no repeated type, counts in order: descending, ties in TIMWOODS order); a `target` value outside §3.2's grammar; a `gemba (targeted)` value that is none of `none (…)`, `not captured (…)`, or a text starting `item #<digits> row <digits> `. The check reads **only the prefix** of a walk line, never its content.
- `gemba cite missing` / `gemba no-walk line missing` (key `5 whys`), v2 with a multi-line chain only: when `gemba (targeted)` starts `item #`, some `  <n>. Why` line must contain `evidence: gemba `; when it starts `none` or `not captured`, a line `  gemba: no walk (` must exist between `- 5 whys:` and the first numbered line.

v1 checks the v1 key list only and passes **every A3 that 2.2.0 posted** (the worked example of a3.md section 3 is the fixture). It does not test reasons or content of the v1 lines beyond the findings above that apply (missing, blank, out of order, repeated).

Section 9 of a3.md becomes: "Run `bash "<plugin root>/scripts/a3-check.sh" <file>` on the A3 you wrote, before *Post A3* and before every *Edit A3* that rewrites a v2 A3. Do not post on a non-zero exit. [the existing sentence about `before`, `after` and `change` stays word for word]". The script lives under `scripts/`, so the **tooling** fingerprint moves ([94-release](94-release.md)).
