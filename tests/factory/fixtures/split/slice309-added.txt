- **An overturn** becomes a rework task (`Source: lead`) for the role that decided it, picked up in that role's next round; its body names the decision on an `Overturns:` line (one line per decision, in the role's own words from its `Decisions`). The running stage keeps running; never stop it for a correction. Track the correction in the lead state until the role confirms it.
**The closing comment.** When you read a finished result (`Status` other than `working`), in this order: (1) **render** it (`post-text.sh render <draft> <out>`, which scans the draft itself: a hit prints the file and line, writes nothing and exits 1; then post nothing, tell the person, keep the task `Running` and the issue open; exit 3 is a draft outside the result template: no Status, a Summary over 10 lines, or an `Artifacts:` line that is not a list of repository paths, each bad entry named on stderr; then post nothing, keep the task `Running` and the issue open, resume the role to fix its draft and render again); (2) **elide** (`post-text.sh elide <in> <out> <commit URL of the draft's commit>`: each fenced block over 20,000 bytes becomes one line, `[block of <n> lines omitted; see <commit URL>]`) and **split** (`post-text.sh split <in> <dir>`) if the body exceeds 60,000 bytes; (3) **find** existing result comments (*Find result comments*: first line `<!-- factory:result v1 -->`; never by position or time); (4) post it (*Post result*; for a split, part 1 first, read its comment id from the returned URL, replace `FIRST` by it in the later parts, post them); (5) **close** the issue (*Close role task*), never before the comment; (6) set the card by *The board* (`Done`, or `Blocked` for a `blocked` result; a `needs-decision` result is a `Done` task and a `Waiting on you` slice); (7) add the task's row to the ledger's Tasks table. Status, Abnormality and Summary are visible in the comment; every other field is inside one `<details>` element, each field's text the draft's byte for byte.
**Rework.** Findings from QA or security go to the developer (or the role that fixes) as a **new** sub-issue under the same parent: title `rework <k>: <one line>` (`<k>` counting the slice's rework tasks from 1); body: the marker line (the fixing role's own next `<n>`), then the protocol's feedback template (`Source`, `Overturns`, `Findings`, `Re-verify`; `Overturns: none` when the task overturns no decision); the card as for any role task. The earlier task issues stay closed and unedited; a finding is never written into one of them or into a file. A `Source: lead` feedback is a rework task whose body says so. The Tasks table's `Stage` cell reads `Build (round 2)` for the first rework of the build.
