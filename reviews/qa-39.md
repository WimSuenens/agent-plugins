## AC-17 judgement

**AC-17: fail.** **Demo re-run: not demanded.**

I judged it against the v2 template and the worked examples, and against fixtures shaped like the demo. I also replayed the rules on the demo's real transcripts: the Lead session `61c45656…` and agents `a37df…` (developer) and `a85f55…` (QA).

No notice reached the Lead, and v2 has no rule that sees them. All 71m stay in agent working, and a transcript with such a cut-off passes `--require-end`.

## Findings (round 4)

### F1 — `references/hansei.md` §1 *Taking the start from the transcript* (contract 39-stage-log §3) — major, blocks — the stall/interruption start command returns the notice time

- Reproduction: build the demo developer's transcript shape (`tests/factory/test_standard_text.sh`, fixture `dev-stalled.jsonl`): a tool result at `2026-11-04T23:50:46Z`, then `[Request interrupted by user]` at `2026-11-05T00:05:54Z`. The watchdog writes that entry at the moment the notice arrives (real transcript `agent-a37df3717d6edee1d.jsonl`: entry 00:05:54.064, notice 00:05:54.050). Run the text's command `tail -n 1 <transcript> | jq -r .timestamp`. Test: `stall-start-is-last-entry-before-gap` (skip).
- Expected: `2026-11-04T23:50Z`, the "last entry before the gap" the same paragraph defines. That gives a 15m stall.
- Actual: `2026-11-05T00:05Z`, the notice's own marker. The stall reads ~0–1m, and 15m goes to agent working. Every role stall loses at least the 600s watchdog window this way, which is the outcome the architect's decision rejected. For the Lead's own transcript, `tail -n 1` read after the resume returns the current turn, so the gap reads ~0.
- Required fix: the architect states the selector, then the developer copies it. For example: the `timestamp` of the last entry before the first `[Request interrupted` / API-error entry that ends the run, and for the Lead the last entry before the person message that set it going. The jq could be `jq -rs '[.[] | select(.timestamp and (.type=="user" and ((.message.content|tostring)|test("\\[Request interrupted")) | not))] | last | .timestamp'`, restricted to entries before the gap.

### F2 — `references/hansei.md` §1 kinds table, rows `stalled`/`interrupted`, "for you" (contract 39-stage-log §3) — minor — the Lead's own sleep interruption in the demo matches no detection rule

- Reproduction: Lead transcript `61c45656…jsonl`: the last entry before the gap is the assistant line `API Error: Your computer went to sleep mid-response.` (`isApiErrorMessage: true`, `error: server_error`) at 02:00:45Z, after its last working entry at 01:43:18Z. The person's `continue` came at 06:49:23Z. `hansei.md`'s Lead rule needs "a tool result with no reply after it, or `[Request interrupted …]`". Neither is the case. The `interrupted` row's first signal is "a role's failure notice", and the Lead has none. Test: `lead-api-error-detected` (skip).
- Expected: the demo's ~5h06m Lead interruption is an `interrupted` wait by the text's own rules.
- Actual: by the letter it is no wait at all, and the 5h stay in agent working. `run/SKILL.md` *Interruptions* ("`interrupted` for … a machine sleep", "`lead` for yourself") probably leads the Lead to the right answer, which is why this is minor.
- Required fix: add the Lead's own `API Error:` line (and any assistant entry the session marks as an API error) to the Lead's detection, with start = last entry before it.

### F3 — `references/hansei.md` §1 and measure 5; `scripts/token-spend.sh --require-end` (contracts 39-stage-log §3, 39-plugin-scripts §3) — major, blocks — cut-offs an agent recovered from are invisible to measures 1 and 5

- Reproduction: demo QA transcript `agent-a85f55ebb2244ed91.jsonl`. Between 00:08Z and 01:21Z it holds three `isMeta` user entries `Your response above was cut off mid-stream …` (00:14:49, 00:32:17, 00:48:14) and two `isApiErrorMessage` / `server_error` entries `API Error: Your computer went to sleep mid-response` (01:04:10, 01:21:35). Each comes after a 7–17m gap, about 71m in all. The agent went on after each, and no failure notice reached the Lead. Another real transcript on this machine (`agent-acb8823b51ee7256e.jsonl`, an unrelated project) has one such sleep cut and ends on a normal `SubagentHandback` result: `--require-end` exits 0 on it. Tests: `in-run-cutoffs-detected`, `require-end-sleep-mid-run-exit-6`, `require-end-cut-mid-stream-exit-6` (skips).
- Expected: by the contract's own premise ("a transcript cut by a stall or an interruption lost the request in flight"), these cut-offs are stalls or interruptions. Their time should be in `stalled`/`interrupted` when held, and the role's spend should read `not captured (transcript truncated by …)`.
- Actual: v2 opens waits only from failure notices (or the Lead's own stall), so none of the 71m is a wait. It all counts as agent working. Here the QA's spend is saved only by its *final* stall. An agent that recovers and hands back normally gets a spend number that is short by the lost requests.
- Required fix (architect first, it is a contract gap): at close, the Lead scans each role transcript for in-run cut-off entries and logs a wait for each from the previous entry's timestamp to the cut-off entry's. Kind: `interrupted` for an API error, `stalled` for a mid-stream cut, `pmset` deciding as now. Held as usual. `--require-end` gains a third rule (any such entry → exit 6). These are undocumented Claude Code transcript fields (`isApiErrorMessage`, `error`, the `isMeta` cut-off text), so the architect may prefer a looser match. Whatever the choice, it has to catch both demo shapes.

The person should know the record will show more `not captured` spend than v1 did.
