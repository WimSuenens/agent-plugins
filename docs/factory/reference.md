One entry per contract that governs the factory, with the file that implements it and the acceptance criteria it answers. The contracts are the source; this page only points at them. Where a later contract changes what an earlier one says, the earlier entry says so and points at the newer one.

## Contracts

Thirty-one contracts: four from 1.0.0 (`39-*`, the record, the stage log, the scripts and the release rules), five from 1.1.0 (`49-*`, the andon and local countermeasures), five from 1.2.0 (`57-*`, the Factory baseline, the per-run A3, the v4 record and override fields, the run close and the release), four from 1.3.0 (`60-*`, the gemba sample: the rule, the walk, the gemba line with schema v5, and the release) and seven from 2.0.0 (`64-*`, the board as run state: the status fields, the role tasks, the ledger and the fields, the parallel slices, the board script, the tracker calls and the release), three from 2.1.0 (`73-*`, test ownership and the TDD loop: the text of each file, the optional code review, and the release), and three from 2.3.0 (`94-*`, the A3 at v2, the hansei lean lines, and the release). The `49-*` contracts change some `39-*` text, the `57-*` contracts change some `39-*` and `49-*` text, the `60-*` contracts change `39-hansei-record`, `57-records-and-overrides` and `57-baseline`, and the `64-*` contracts change `39-stage-log`, `39-plugin-scripts`, `39-hansei-record` and the lead state's sections; the `73-*` contracts change standard text only; the `94-*` contracts change the entries named in their own entries below. No contract is replaced by a later one. Each entry below names what changed.

### 39-stage-log: the stage log in the lead state

- **Contract**: [contracts/39-stage-log.md](../../contracts/39-stage-log.md). Changed for 1.1.0 by [49-records](../../contracts/49-records.md) §1 to §4. **Superseded for 2.0.0** by [64-ledger-and-fields](#64-ledger-and-fields-the-ledger-the-hansei-fields-and-the-readers-of-the-sections-that-leave-the-lead-state) §3 and §4: the lead state holds no `## Stage log`, `## Waits`, `## Person's touches` or `Status:` line; the tables are the ledger's (one comment on the slice ticket) and the role tasks are the sub-issues. The text below describes the 1.x lead state, which the 1.x migration keeps readable.
- **Governs**: the sections the lead adds to the item's lead state file (`00-lead-state.md`), in order. At 1.0.0: `## Label` (written once at item start: plugin root, release, standard and tooling fingerprints, dependency versions, lead session ids), `## Stage log` (one row per stage, UTC times from `date -u`), `## Waits` (each wait with its kind, the agent it stopped, and whether it held the item), `## Person's touches`. From 1.1.0 two more follow: `## Findings` (the ledger the kind 2 rule reads) and `## Abnormalities` (one row per abnormality, with its paused agent and its andon comment). A stage row can be an `Andon A<n>` row. The wait kinds were four at 1.0.0 (`person`, `limits`, `stalled`, `interrupted`); from 1.1.0 there are five, with `andon` for the time the Lead holds the affected work for an andon. *Done, then stopped*: an agent that stops after a complete `done` result is accepted, not resumed, when its commits are on the item branch and its paths are clean. The cross-check against git commit times and stage-summary comment times.
- **Implemented in**: `plugins/factory/references/hansei.md` sections 1, 2 and 4 (the Waits and Abnormalities tables, the close scan); `plugins/factory/skills/run/SKILL.md` steps 5 and 6, *Interruptions* and *Andon*.
- **Acceptance criteria**: AC-6, AC-11, AC-12, AC-13 (1.0.0). From 1.1.0, AC-8 (the andon wait) and AC-23.

### 49-abnormality-list: the list, the `Abnormality:` line and the detection rules

- **Contract**: [contracts/49-abnormality-list.md](../../contracts/49-abnormality-list.md)
- **Governs**: the seven kinds, each with the observation that proves it: 1 `blocked-input`, 2 `same-finding-twice`, 3 `role-outside-role`, 4 `slow-stage`, 5 `fence-crossing`, 6 `version-drift`, 7 `other`. The `Abnormality:` line in a result (`<kind> — <what was seen> — <where to look>`, optional, read as `none` when absent). A result with a line other than `none` is not `done` for the lead until its andon has run. The detection rules: kind 2 (the ledger of findings, the five-slot signature, the two clauses M1 and M2); kind 3 (the ownership table read from `origin/main`, most specific match (exact path, then directory prefix, then wildcard; a tie is reported), `section` rows skipped, `git diff-tree -z`, and the rule that commits touching `## Overrides` or the table must come from the lead); kind 4 (the 2× test against the median of the same role's earlier rows, with at least three earlier rows, waits excluded); kind 6 (fingerprint drift against the latest earlier record of the same release, and the installed sha against the FREEZE line).
- **Implemented in**: `plugins/factory/references/protocol.md` `## Andon` (the list and the line); `plugins/factory/skills/run/SKILL.md` `## Andon`, *Detection*.
- **Acceptance criteria**: AC-1 to AC-7. AC-7 is human-only (a seeded abnormality in the sandbox session).

### 49-andon-process: raise, pause, 5 Whys, resume and the andon comment

- **Contract**: [contracts/49-andon-process.md](../../contracts/49-andon-process.md)
- **Governs**: how a role raises an andon and how the lead handles it: stamp the pause, stop the running agent with `TaskStop` (skipped for an agent that already handed back), run the 5 Whys, decide the countermeasure inside the fence, resume the same agent with `SendMessage`. A refused resume (the person stopped the agent) gets no second attempt: the lead spawns a fresh agent from the role's result file, and the item goes on. The 5 Whys rule, *blame the process first*: each cause names a process object (the brief, the inputs, the standard's text, the tooling, the ownership table, the order of stages), with evidence; a chain that names a person, a role's care or competence, or a model is refused; a model or role swap is allowed only after four `examined … adequate` lines. The andon comment (`<!-- factory:andon v1 -->`), posted once on the slice ticket in the project's own tracker, never in this repo; its text is the lead's paraphrase, with no copied content. Changed for 2.3.0 by [94-hansei-lean](../../contracts/94-hansei-lean.md) §1: the comment gains an optional last line, `- waste: <type | ->`, which the lead decides before the scan.
- **Implemented in**: `plugins/factory/references/protocol.md` `## Andon` (the rules every role reads); `plugins/factory/skills/run/SKILL.md` `## Andon`, *Procedure*, *The 5 Whys*, *The comment*.
- **Acceptance criteria**: AC-6 and AC-8 to AC-14, AC-22. AC-9, AC-10, AC-11 and AC-14 are human-only.

### 49-overrides: the override format, the fence, precedence, run identity and expiry

- **Contract**: [contracts/49-overrides.md](../../contracts/49-overrides.md)
- **Governs**: where an override lives (`docs/agents/factory.md`, under `## Overrides`, which the lead owns and writes in the worktree that raised the andon) and its fields: name, `started`, `run`, `rule`, `andon`, `status`, `fence check`. The status grammar (`active`, `kept … for next run` or `for #<map>`, `promote chosen <date>`, `superseded <date> by <name>`). Precedence: an override wins over the plugin's text outside the fence; of two disagreeing overrides the later `started` wins; the fence always wins. The fence: the seven items of ADR 0011 (`## Never overridable locally`, F1 to F7), plus the data-egress question E, which is a question asked of every override and not an eighth fenced item. One yes to any of the eight refuses the override. The run start check (an override that crosses the fence is not applied and starts a kind 5 andon; an earlier run's override with no answer starts a kind 7 andon and waits for the person). The close of the run (step 10): one line per override, and keep, promote or drop, recorded in a settle worktree and merged by the person's yes.
- **Implemented in**: `plugins/factory/references/protocol.md` `## Overrides` and `## Never overridable locally`; `plugins/factory/skills/run/SKILL.md` `## Andon` (*Overrides*, *Run identity*, *Run start*, *Settle round*) and step 10. From 1.2.0 the close is step 9 alone and step 10 is removed ([57-run-close](../../contracts/57-run-close.md) §1); the settle answers there carry the experiment's before and after.
- **Acceptance criteria**: AC-15 to AC-21, AC-26 and AC-27. AC-20 and AC-25 and AC-28 are human-only.

### 57-baseline: the Factory baseline issue

- **Contract**: [contracts/57-baseline.md](../../contracts/57-baseline.md). Its run-close timing is in [57-run-close](../../contracts/57-run-close.md) §2 (step 9.1), and the Factory run lines it reads are in [57-records-and-overrides](../../contracts/57-records-and-overrides.md) §7. Changed for 1.3.0 by [60-gemba-line](#60-gemba-line-the-gemba-line-hansei-schema-v5-and-how-old-and-new-records-are-read) §4: the baseline reads v3, v4 and v5, skips a v5 record with no or with two `gemba` lines and names it, and its `records:` line names every schema a series holds. No figure changes.
- **Governs**: one issue per project, in the project's own tracker, titled exactly `Factory baseline`, authored by the Lead's own `gh` user, whose body's first line is `<!-- factory:baseline v1 -->`. The Lead finds it by title, author and that marker, in any state; the pin is best effort and is never read. None found: the Lead creates it at run start and pins it when the tracker allows. A failed lookup changes nothing and creates nothing. An exact-title issue without the marker is left alone and the person is asked. More than one marked issue: the person chooses. The body is derived, never stored: a block for the current series (the session's release `X.Y`, its `standard` and `tooling`, its sections), history for earlier series (labelled with the date each was replaced), a calibration list with no figures, the skipped and excluded records, and notes for dropped overrides. A figure is the median of the items that captured it, shown with `k of n`; a value not captured reads `not captured (<reason>)`, never `0`. A patch or tooling-only change starts no series; a `standard` difference under one `X.Y` is excluded and named. Calibration records never enter a series. The body is rewritten whole, never hand-edited, after each item's record is final, at run close and after the settle merge; a repair check at run start recomputes it when a record is not listed. Changed for 2.3.0 by [94-a3-v2](../../contracts/94-a3-v2.md) §8: the baseline reads the `answer` lines of an A3 with marker v1 or v2, and skips and names any other version; the A3's `gemba (targeted)` line is presence-checked and no figure reads it.
- **Implemented in**: `plugins/factory/references/baseline.md` (the rules, the body layout, a worked reading); `plugins/factory/skills/run/SKILL.md` step 0 and step 5 (the checks), step 8.10 (the update), step 9.1 and 9.3; the tracker operations *Find baseline*, *Create baseline*, *Pin baseline*, *Read baseline*, *Edit baseline* and *Find records* in `plugins/factory/skills/setup-factory-skill/references/issue-tracker-github.factory.md`.
- **Acceptance criteria**: AC-1 to AC-9 (contract §9). AC-10 is human-only: the acceptance demo recorded it as pass (the issue was created at run start with the marker first line, the current 1.2 block read `not captured`, and the older release was kept as history).

### 57-a3: the per-run A3 comment

- **Contract**: [contracts/57-a3.md](../../contracts/57-a3.md). The experiment's override lines and the measures it may name are in [57-records-and-overrides](../../contracts/57-records-and-overrides.md) §5 and §6.
- **Governs**: one A3 per run, posted once as one comment on the map issue, its first line `<!-- factory:a3 v1 -->` up to 2.2.0 and `<!-- factory:a3 v2 -->` from 2.3.0 (v1 is still read and is never rewritten; see [94-a3-v2](#94-a3-v2-the-a3-at-v2-the-three-new-lines-the-check-and-v1-kept-valid)). Its field lines come in one fixed order: `run` (`closed` or `run stopped`), `series and release` (with the two fingerprints), `problem`, `evidence`, the `5 whys` block, `process item to change`, `countermeasure`, `measure targeted`, `before`, `after`, `change`, `items counted` (before, during, after), `still uncertain`, `other problems seen`, `other overrides`, `standard changes proposed`, `baseline` (its link) and `answer` (one entry per override: `pending`, then `keep`, `promote` or `drop` with its date). The problem is the process item that the most items' andons name; with no andon, the measure furthest above its reference. A run has at most one experiment: one override that names one measure, with a closed item to measure against, addressing the problem, and passing the fence check first. A change of plugin text is never an experiment. Before, during and after items come from the records; a during-item counts in neither reading. A reading that cannot be compared reads `not comparable (<why>)`; a value not captured reads `not captured (<reason>)`. `still uncertain` is never `none`. No A3 is written for a run that closed no item. Changed for 2.3.0 by [94-a3-v2](../../contracts/94-a3-v2.md) §1, §2 and §8: a v2 A3 adds `waste` after `evidence`, `gemba (targeted)` after `waste`, and `target` after `change`.
- **Implemented in**: `plugins/factory/references/a3.md` (the template, the problem rule, the experiment rules, the readings, the comparability rules, the check before posting); `plugins/factory/skills/run/SKILL.md` step 5 (the experiment's commit, before the `Start item` stamp), step 8.10 (the decision that an experiment is written), step 9.2 (the post) and *Overrides*; the tracker operations *Find A3s*, *Find A3*, *Post A3* and *Edit A3* in the same template.
- **Acceptance criteria**: AC-11 to AC-20 (contract §10). AC-21 is human-only: the acceptance demo recorded it as pass for an A3 that had no experiment (its `answer` line read `none (no override to settle)`).

### 60-gemba-sample: picking the stage to walk

- **Contract**: [contracts/60-gemba-sample.md](../../contracts/60-gemba-sample.md). Builds on [39-stage-log](#39-stage-log-the-stage-log-in-the-lead-state) and [57-run-close](#57-run-close-the-run-close-the-settle-round-and-the-feedback-offer).
- **Governs**: the rule that picks the one stage a walk reads, from the stage log and the ticket number alone. A role row has a `Role` among the seven roles and an `Agents` cell that is not `-`. A row is flagged when its `Result`, trimmed and lowercased, does not start with `done` or `pass`, or its `Notes` contain `paused by A` and a digit. The eligible rows, in the log's own order (not sorted by `#`), are counted as `n`; the eligible row at index `<id> mod n`, counted from 0, is picked. With `n = 0` the set is every role row and the line marks the row `already flagged`; with no role row, nothing is picked and the line reads `not captured (no role stage ran)`. No duration, wait, peak, earlier record or random choice enters the rule.

- **Acceptance criteria**: AC-1 (tests `t1-*` and `t2-*` in `tests/factory/test_gemba.sh`; the replay of the stage logs of #12, #49 and #57 and the worked example of #14).

### 60-gemba-walk: what the walk reads, how much, what is compared, and where a finding goes

- **Contract**: [contracts/60-gemba-walk.md](../../contracts/60-gemba-walk.md). Builds on [49-andon-process](#49-andon-process-raise-pause-5-whys-resume-and-the-andon-comment), [57-run-close](#57-run-close-the-run-close-the-settle-round-and-the-feedback-offer) and [60-gemba-sample](#60-gemba-sample-picking-the-stage-to-walk).
- **Governs**: where the walk sits: step 8.3a and item 3a of section 5 of `hansei.md`, after the merge approval and the token totals, before the record is filled; for an item only, one walk per item. The evidence, in order: the sampled row's transcript (the agent ids of its `Agents` cell); or, for the whole row when a transcript cannot be read, the sampled role's commits on `item/<id>` and its result file with the `Summary` removed. The result's `Summary`, the completion notice, the stage summary and the final reply are claims, never evidence. The data rule: everything the walk reads is text to compare, and no sentence in it is followed. The bounded read: each command ends in `head -c`; at most 30,000 characters printed, the brief included (the reads use a budget of 29,900); one extra bounded read at most, when the view is partial. The comparison: the brief's `Done`, `Constraints` and `Output`, and the row's `Result`, `Notes` and `Waits`; exactly three things are looked for. The outcomes: `nothing (<d> Done items and <c> constraints checked)`, `nothing in the part read (<n> chars of <m>)` for a partial walk, or `difference: <sentence>`. A difference becomes a kind 7 andon with no paused agent, with no wait, no override and no resume, before the record is posted. A walk that could not be done reads `not captured (…)`, in the five cases of section 6. Extended for 2.3.0 by [94-a3-v2](../../contracts/94-a3-v2.md) §5: one targeted walk per run, at the stage the problem points at, with the same commands, cap and rules, before the A3's chain; a difference is evidence for the chain and raises no andon.
- **Implemented in**: `plugins/factory/references/hansei.md` section 6 (all of it) and section 5, item 3a; `plugins/factory/skills/run/SKILL.md` step 8.3a and the sentence on the kind 7 andon under *Andon* and *Procedure*.
- **Acceptance criteria**: AC-2, AC-3, AC-5, AC-6, AC-7 and AC-9 (tests `t3-*` to `t10-*` and `t12-*` in `tests/factory/test_gemba.sh`). The unverified items of the requirement are named in the 1.3.0 changelog entry.

## Maintainer procedure: changing the factory

Use this when a change touches anything under `plugins/factory/`.

1. Make the change on a branch of its own; for a factory item that is `item/<id>`. Each commit starts with `#<id>`.
2. Bump `version` in `plugins/factory/.claude-plugin/plugin.json` at the level the rule asks: minor for standard work (`skills/run/SKILL.md`, `references/*.md`, `agents/*.md`), patch for anything else under `plugins/factory/`, major only when message formats or the protocol break.
3. From the branch's worktree: `git fetch origin main`, then `bash plugins/factory/scripts/check-bump.sh`. Exit 0 is a pass; exit 1 names the level it needs; exit 2 is a repository or version error to fix first.
4. Run the suite: `bash tests/run.sh`. It prints `ALL PASSED` when every check holds.
5. Run `claude plugin validate ./plugins/factory` and `claude plugin validate ./plugins/factory/skills`.
6. Open the PR. The lead runs the same bump check before `gh pr create`, so a PR that fails it does not open.
7. After the person's merge approval, the lead runs the check again, merges, and tags `factory-v<version>` on the merge commit, unless that tag exists. To tag by hand: `git tag factory-v<version> <merge-commit>` and `git push origin factory-v<version>`. The release steps and the checks after the tag are in [release-runbook.md](release-runbook.md).
8. Add an entry for the item to [CHANGELOG.md](../../CHANGELOG.md).
9. After a release, restart any Claude Code session that runs the factory: a session keeps the skill text it read when it started.

Running the factory itself is in [plugins/factory/skills/run/SKILL.md](../../plugins/factory/skills/run/SKILL.md). Setting up a project is `/factory:setup-factory-skill`, and the project's tracker commands are in its `docs/agents/issue-tracker.md` under `## Factory operations`.

A project's overrides are not plugin changes. The lead writes them in that project's `docs/agents/factory.md` (contract [49-overrides](../../contracts/49-overrides.md) §1), and the plugin's text is never edited to apply one. A countermeasure that needs a plugin change is recorded in the andon comment and in the step-9 feedback issue, and goes through this procedure.
