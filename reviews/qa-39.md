## Findings

Round 2: F4, F5, F6: **fixed** in `9ee1cdc` and re-verified in round 3. Security L1a: **fixed** in `9ee1cdc`, with QA tests `newline-*`. The round-2 write-ups are kept below for the record.

### F4 — contract 39-plugin-scripts, common rules and §3 — minor, does not block — token-spend exit 3 leaks jq's error with the absolute transcript path

- Reproduction: a transcript that is valid JSON but the wrong shape, e.g. a line `[1,2]`, or an assistant entry with `"timestamp":"soon"` read with `--since 2026-01-01T00:00Z`. Run `bash plugins/factory/scripts/token-spend.sh --since 2026-01-01T00:00Z <dir>/ts.jsonl`. Test: `test_token_spend.sh` `wrong-shape-contract-line-no-path` (skip).
- Expected: exit 3, and stderr is exactly `token-spend: transcript ts.jsonl unreadable`. No absolute path: "a stderr line can be copied into a record on a public tracker".
- Actual: exit 3 (right), but stderr has two lines: `jq: error (at /private/tmp/…/ts.jsonl:1): date "soon" does not match format …`, then `token-spend: a transcript is unreadable or not JSON (one of: ts.jsonl )`. On a real run, the first line holds `/Users/<name>/.claude/projects/…`.
- Why it does not block: the Lead's table for exit 3 has it write the fixed form `not captured (transcript <basename> unreadable)`, not the stderr line, and real transcripts are objects with ISO timestamps.
- Fix (developer): send the main `jq` call's stderr to `/dev/null`. Name the failing file, for example by running the main jq once per file with `jq -e 'type == "object"'`, or by validating each file's shape in the per-file loop.

### F5 — contract 39-standard-changes §5 — low, does not block — the tag's semver check accepts leading zeros

- Location: tracker patch, *Merge PR* item 1: `grep -Eq '^[0-9]+\.[0-9]+\.[0-9]+$'`.
- Reproduction: `printf 1.08.0 | grep -Eq '^[0-9]+\.[0-9]+\.[0-9]+$' && echo tagged`. Test: `tag-regex-rejects-leading-zeros` (skip).
- Expected: the contract's regex `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`. Actual: `1.08.0` passes.
- Why low: the bump re-check just before `gh pr merge` refuses a branch at `1.08.0` (exit 1, tested), so the tag step never sees one in the normal order.
- Fix (developer): use the contract's regex.

### F6 — contract 39-hansei-record §5 — low, does not block — *Post hansei* has no `mktemp` scratch file

- Location: tracker patch, *Post hansei*: `gh issue comment <id> --body-file <record>.md`. Only *Edit hansei* says where `<record>.md` comes from.
- Reproduction: `grep -F -- '- **Post hansei**' plugins/factory/skills/setup-factory-skill/references/issue-tracker-github.factory.md | grep -c mktemp` prints `0`. Test: `post-hansei-mktemp` (skip).
- Expected: `rec="$(mktemp)"`, write the template to `"$rec"`, `--body-file "$rec"`, then `rm -f "$rec"`, as the contract writes it.
- Actual: the Lead can pick any `<record>.md`, including one inside the worktree, which a later `git add -A` could commit.
- Fix (developer): copy the contract's *Post hansei* wording.
